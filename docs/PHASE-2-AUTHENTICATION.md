# Phase 2 Authentication & Account Architecture

Phase 2 implements Founder-controlled Board accounts using Firebase Authentication and Cloud Firestore only. The production client remains a static GitHub Pages application.

## User experience

Ordinary directors do not enter an email address, username, or conventional password.

### First use

1. Founder Director creates the Board account.
2. The portal generates a one-time activation code and displays it once to the Founder.
3. The director opens the portal and enters their full name.
4. The portal prompts for the one-time activation code.
5. After successful Firebase Authentication, the director chooses a four-digit PIN.
6. The Firebase Auth credential is updated and the Firestore account is marked active.

### Normal sign-in

1. Enter full name.
2. Enter four-digit PIN.
3. Firebase Authentication establishes the portal session.
4. Firestore Security Rules authorize access based on the immutable Auth UID and director profile.

## No director email addresses

Firebase Email/Password Authentication is used only as the underlying credential provider because this project has no application server or Cloud Functions.

Each account receives a random non-deliverable internal Auth alias such as:

`dir-<random>@tpp-directors.invalid`

The alias is generated by the portal. It is not the director's email address and is never presented as a login identifier.

## Full-name lookup

A normalized full name is SHA-256 hashed in the browser. The hash becomes the document ID for:

`loginDirectory/{loginKey}`

The login directory record contains only the minimum data required to connect the human-friendly name flow to Firebase Authentication:

```text
loginDirectory/{sha256(normalizedName)}
  directorUid
  authEmail
  activationRequired
  createdAt
  updatedAt
  activatedAt
```

Security Rules allow an unauthenticated client to `get` one exact login-directory document, because that lookup must happen before Firebase sign-in. Public collection listing is denied.

This architecture intentionally does not expose a query that lists Board identities.

### Duplicate full names

Because the requested public login identifier is only the person's full name, two active accounts with exactly the same normalized full name are ambiguous. Phase 2 therefore rejects an exact duplicate name during account creation. A later identity-disambiguation workflow can be added if the Board ever has two directors with the same full legal name.

## Four-digit PIN handling

The raw four-digit PIN is never written to Firestore.

The PIN is converted in memory into an account-specific Firebase password value that satisfies Firebase Authentication credential requirements. Firebase Authentication stores/verifies the password credential; Firestore stores only account metadata.

A four-digit PIN has limited entropy. The project relies on Firebase Authentication's own service-side abuse/throttling protections plus generic login errors. Client-only lockout controls are not treated as a security boundary because a determined user can bypass static JavaScript.

## Founder account provisioning

Creating a Firebase Email/Password account signs the Auth instance in as that new user. The portal therefore initializes a second Firebase app named `accountProvisioner` with in-memory Auth persistence.

Founder account creation uses that isolated Auth instance so the new director account can be created without replacing the Founder Director's primary authenticated portal session.

After Auth creation, the Founder session performs one Firestore transaction that:

- allocates the next `DIR-######` from `system/counters`;
- creates `directors/{newUid}`;
- creates `loginDirectory/{loginKey}`;
- advances the counter;
- creates an immutable account-creation audit event.

If the Firestore transaction fails immediately after Auth creation, the provisioning client attempts to delete the newly created Auth user before ending the provisioning session.

## Founder root invariants

The Founder Director is still a separately bootstrapped root identity:

```text
systemRole: "founder_director"
root: true
permissions: ["*"]
```

Ordinary Founder account administration cannot create a second root identity, promote an ordinary account to Founder Director, delete the root account, or demote it.

## Permission model

Phase 2 introduces capability strings rather than relying only on titles. Initial templates include Standard Director, Board Secretary, Board Chair, and Treasurer.

Examples:

```text
directors.view
directors.create
directors.update
permissions.manage
meetings.view
meetings.create
meetings.activate
meetings.attendance.manage
votes.cast
votes.push
votes.close
documents.view
documents.submit
documents.review
resolutions.view
resolutions.create
minutes.view
minutes.edit
audit.view
```

The Founder root profile implicitly has every capability. Templates are only starting points; direct per-account permission editing is completed later in Phase 2.

## No composite/manual indexes

This project does not define or deploy composite/manual Firestore indexes.

Phase 2 account operations use:

- direct document reads;
- unfiltered collection reads available only to the Founder;
- a single counter document transaction;
- client-side sorting for the Board account roster.

`firestore.indexes.json` is intentionally absent, and `firebase.json` deploys Firestore rules only.

Future phases must preserve this constraint unless the project requirements are explicitly changed.

## Static-client limitation: privileged PIN reset

Firebase's privileged user-management APIs require a secure Admin SDK environment. This project intentionally has no Functions or application server.

Therefore, Phase 2 can securely implement:

- Founder-created accounts;
- first-use activation;
- self-selected PIN;
- normal PIN sign-in;
- Firestore account suspension/status controls;

but it cannot safely let a Founder browser session directly replace another user's Firebase Authentication password.

Until a secure backend is permitted, a forgotten-PIN reset that requires changing the Auth password must be performed through Firebase's administrative console/workflow and then reconciled with the Board account state. The portal must not fake privileged password reset by storing PINs or reset secrets in Firestore.
